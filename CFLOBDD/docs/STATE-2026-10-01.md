# Part A — Project-wide (all platforms)

## The devcontainer is gone

`.devcontainer/` (Dockerfile, devcontainer.json, init-firewall.sh) was removed in commit
`c94b315`. If you were using "Reopen in Container", that path no longer exists. The
**Linux/macOS branches of the Makefiles are untouched** — the repo still builds natively on
Linux with system Boost (`libboost-all-dev`); it simply no longer ships a container recipe.

## Per-width targets are `build-N`, not `cflobddN`

Renamed in commit `4c55abf`, and the reason is Linux-specific, so it is worth knowing:

```
make build-32        # produces cflobdd32$(EXE_EXT)
make all-bit-sizes   # all nine: 32, 64, 128, 256, 512, 1024, 2048, 4096, 8192
```

On Windows `EXE_EXT = .exe`, so a phony target `cflobdd32` and the produced
`cflobdd32.exe` are distinct. **On Linux `EXE_EXT` is empty**, so the phony target and the
real file collide and make re-enters the recipe indefinitely. Hence the `build-` prefix.

Each `build-N` recipe deletes the `NUM_BITS`-sensitive objects
(`multiplication_crt.o tests_cfl.o cflobdd_c.o return_map_specializations.o`) and re-invokes
make with `-DNUM_BITS=N`, so every width recompiles those four files and relinks a ~39 MB
binary.

`examples/Makefile` passes `-std=gnu99` to CUDD's C sources because `gcc-14` defaults to C23,
which rejects CUDD's implicit function declarations.

## Open: a ~3× performance regression at 32 bits

This is the live question and it is platform-neutral.

Measured 2026-09-30 at commit `9559f13`, a clean full rebuild:

```
./cflobdd32 shiftadd-all  ->  230, 182, 192 ms   ("...Moduliwise took")
                              modulus 59: 35, 22, 29 ms
```

Baseline recorded in `CFLOBDD/cflobdd-mult-tests-04-17-2026.txt`:

```
shiftadd-all  -> 59, 69, 63, 64 ms ; modulus 59 -> 9-11 ms
karatsuba-all -> 613 ms
BuildMultiplicationSpecsModuliwise -> 2 ms ; MultModK(59) -> 0 ms
```

### Ruled out: `CFLOBDD_MAX_LEVEL`

It is **22** (`cflobdd_node.h:199`), raised from 13 by commit `8540060` on 2026-03-24 to
support 8192-bit — three weeks *before* the 04-17 baseline, so that baseline already paid the
padding cost. For `NUM_BITS=32` the topmost embedding gives `virtualMaxLevel = 6`,
`bottomLevel = 16`, `stride = 65536`; everything below `bottomLevel` is `NoDistinctionNode`
padding. Wasteful, but not the regression.

### Prime suspect: hash-table tuning that was never committed

`git log -S "20000000" --all` finds nothing in `CFLOBDD/hash.cpp` or `hashset.cpp`. There is
no stash and no branch carrying it. Committed values:

| Constant | File:line | Committed | Prior session's notes recorded |
|---|---|---|---|
| `HASH_NUM_BUCKETS` | `hash.cpp:11` | 200,000 | 20,000,000 |
| `HASHSET_NUM_BUCKETS` | `hashset.cpp:11` | 2,000,000 | 20,000,000 |
| `RETURN_MAP_NUM_BUCKETS` | `hashset.cpp:12` | 4,000,000 | 20,000,000 |
| `REDUCTION_MAP_NUM_BUCKETS` | `hashset.cpp:13` | 4,000,000 | 20,000,000 |
| `NODE_TABLE_NUM_BUCKETS` | `hashset.cpp:14` | 4,000,000 | 20,000,000 |

A measurement from an earlier session recorded raising buckets 200K → 20M as taking 128-bit
`shiftadd-all` from **127 s to 52 s (~2.5×)**. That tuning evidently lived as working-tree
edits and was never committed, and the current binaries are built from a clean tree. Branch
check: `sequitur`, `multiplication`, `main` all carry 200,000/2,000,000; `origin/opts`
diverges with `MAX_LEVEL 30` and `HASHSET 200000`.

**Lesson worth acting on: commit performance tuning, or it evaporates.**

### Not yet tested: freelist caps

`cflobdd_config.h` defaults `node`/`pairProduct`/`tripleProduct`/`reductionMap` freelist caps
to **64**, `returnMap` to 0 (unlimited). Testable with no rebuild:

```
./cflobdd32 --freelist-cap=0 shiftadd-all
./cflobdd32 --freelist-cap=1000000 shiftadd-all
```

Other runtime flags: `--flat-lookup-threshold` (default 2^25), `--compose-flat-threshold`
(2^25), `--identity-map-threshold` (1024), `-v`, `--help`.

## Toolchain

| Component | Value |
|---|---|
| `make` | `C:\cygwin64\bin\make.exe` (Cygwin), first on PATH |
| Compiler | MSYS2 UCRT64 g++ **15.2.0**, pinned by absolute path |
| Cygwin g++ | **13.4.0** at `C:\cygwin64\bin\g++.exe`, second on PATH |
| Boost | 1.81.0 at `../../boost_1_81_0/` |

`CFLOBDD/Makefile`'s Windows branch (commit `9559f13`):

```make
MSYS2_GXX        := C:/msys64/ucrt64/bin/g++.exe
ifneq ($(wildcard $(MSYS2_GXX)),)
    CXX_DEFAULT  := $(MSYS2_GXX)
else
    CXX_DEFAULT  := g++
endif
...
CC = $(CXX_DEFAULT)
```

A bare `g++` resolves from PATH and Cygwin's sits second, so if MSYS2 ever fell behind it the
build would silently switch toolchains, whose objects do not link together. `$(wildcard)`
with a `C:/`-style path was verified under **both** Cygwin make and MSYS2 make, in the found
and not-found directions. `CC` uses `=` not `?=` deliberately: `?=` would defer to a `CC`
inherited from the environment, defeating the pin; a command-line `make CC=...` still wins.
Linux/macOS behaviour is unchanged (`CXX_DEFAULT := g++`). Note this Makefile uses **`CC`**
as the C++ compiler variable — a pre-existing quirk, left alone.

**`.vscode/` is gitignored (`.gitignore:19`).** `tasks.json` was corrected locally to pass
`build-${input:numBits}` instead of the pre-`4c55abf` `cflobdd${input:numBits}`, but that fix
cannot be committed and will be absent on a fresh clone. Re-apply by hand.

Build state: `CFLOBDD/cflobdd.exe` (52,098,630 bytes) and `cflobdd32.exe` exist and are
smoke-tested. `cflobdd64.exe` … `cflobdd8192.exe` have never been built on this machine.

## PATH

User PATH is stored at `HKCU\Environment\Path` as **REG_EXPAND_SZ**, with some entries using
`%USERPROFILE%` literally — which is normal; Windows writes its own WindowsApps entry that
way. **Never edit it with `[Environment]::SetEnvironmentVariable('Path', $v, 'User')`**: that
writes REG_SZ, so either the `%VAR%` entries stop expanding (if you read the raw value) or
the indirection is silently flattened to absolute paths (if you read via the .NET getter,
which expands). Use a raw read plus
`Set-ItemProperty -Path 'HKCU:\Environment' -Name Path -Value $new -Type ExpandString`, then
verify every entry with `Test-Path`. Length is not a tell — `%USERPROFILE%` and
`C:\Users\<user>` can be the same number of characters.

## Claude Code

The **VS Code extension is the only installation**; there is no `claude` command, so
`claude update`, `claude doctor`, `claude --resume` and headless `claude -p` are unavailable.
The extension bundles its own binary under
`%USERPROFILE%\.vscode\extensions\anthropic.claude-code-<version>-win32-x64\resources\native-binary\`
and ignores PATH; VS Code auto-updates it.

A trap worth recording: the standalone CLI had gone stale at 2.1.228 while the extension was
2.1.251, and the old CLI's `--resume` picker listed **nothing**, because the transcripts had
been written by the newer version. That looks exactly like data loss and is not. **If a
resume picker is empty, suspect a version mismatch before suspecting missing files.**

`~/.claude/settings.json` sets `cleanupPeriodDays: 3650`; transcripts had been expiring
silently at the 30-day default and several were lost. 102 were later restored from a
`cp -r` snapshot taken in April.

MCP servers are defined in **two** files, neither of which should be deleted:
`%USERPROFILE%\.mcp.json` (`pdf-reader`, enabled via `enabledMcpjsonServers`) and
`%APPDATA%\Claude\claude_desktop_config.json` (`pdf-reader` and `Wolfram`). `Wolfram`
currently fails with `CONNECTION_CLOSED` even though the kernel and the
`Wolfram/AgentTools` paclet are both installed.
